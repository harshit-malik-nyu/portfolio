# Event contract assurance: decision and acceptance record

Status: independent, AI-assisted work sample. The request, responsibilities and acceptance below are proposed for a hypothetical delivery team. No stakeholder interview, adoption or business sign-off occurred.

## Decision brief

**Decision:** May an event export proceed to further analysis, or must an owner investigate a contract failure first?

**Recommendation:** use the existing local audit as a blocking pre-analysis diagnostic, supported by a separately implemented SQL reference. Do not label its output a cleaned dataset or authorize a release based on CHECKS_PASSED. Require separate reconciliation to an authoritative source before interpreting missing events or conversion.

**Why this matters:** an ID collision can inflate or misattribute metrics even when each individual row looks valid. Retaining the first occurrence silently converts a data-quality dispute into an analytical assumption. Conversely, counting retries as customers inflates the denominator. The reference challenge demonstrates these failure modes without claiming observed company losses.

## Assumed current process and proposed process

| Stage | Assumed current process (not observed) | Proposed process | Decision / output |
|---|---|---|---|
| Intake | Analyst receives an export with implicit event names | Owner declares taxonomy and confirms permission to process the export | Reject missing contract or unsupported input |
| Quality review | Spot checks or first-row deduplication | Validate required fields, calendar timestamps, identity and optional payload consistency | BLOCKED / REVIEW / CHECKS_PASSED |
| Remediation | Fix a dashboard after interpreting anomalies | Assign each finding to the emitting-system or taxonomy owner; preserve the original export | Correct upstream and rerun; no silent repair |
| Interpretation | Treat clean rows as complete coverage | Reconcile source transactions and expected tracking with the export | Proceed only if purpose-specific completeness evidence is adequate |
| Handoff | Send numbers without decision conditions | Share aggregate report, contract, unresolved issues and explicit limitations | Named business owner accepts analytical use, not this tool |

## Options considered

| Option | Benefit | Cost or limitation | Decision |
|---|---|---|---|
| Manual spot checks | No implementation effort | Inconsistent coverage; difficult to reproduce | Useful investigation aid, insufficient as the only gate |
| Existing engine plus reference checks | Repeatable local diagnostic; catches selected plausible semantic defects | Two implementations to maintain; cannot detect an event that never arrived | Selected for this bounded sample |
| Full observability platform | Potential collection monitoring and operational integration | Integration, governance and platform cost; outside the free local scope | Reconsider when scale, retention and monitoring requirements justify it |

No time savings, ROI or avoided loss is asserted. A future evaluation should measure median review time, false positive rate, missed known faults and rework on approved historical exports. Compare the same cases under both methods; define success thresholds before collecting results. Pass fractions in synthetic tests are not estimates of operational accuracy.

## Change request and scope control

**Proposed request:** "Automatically repair the export and let CHECKS_PASSED approve a launch."

**Disposition:** reject as stated. The audit has neither authoritative truth to repair conflicting identities nor source completeness, consent, revenue or experiment-assignment evidence. An automated repair could erase evidence of a defect.

**Accepted alternative implemented in this revision:** expose the assumptions, independent comparison, selected defect challenge and required follow-up in an inspectable review pack. Keep existing CLI exit codes and browser behavior unchanged. Link the pack from the tool and portfolio evidence page.

**Reversal conditions:** consider a separate repair pipeline only with a documented authoritative source, immutable raw retention, approved repair rules, an exception queue, before/after reconciliation and owner acceptance. This record does not claim those capabilities exist.

## Observed defect and implemented correction

During this review, four new regression cases failed against the original UI: a pending file read overwrote a newer contract, file selection or example, and malformed UTF-8 silently produced replacement characters instead of rejecting. The unchanged valid-file control passed. These were reproduced behavior defects, not hypothetical stakeholder feedback.

The correction uses a monotonically increasing request version. Changing the contract, file or example invalidates pending work and clears obsolete reports; a stale read cannot publish, clear a newer report or change the active run button. Files now use fatal UTF-8 decoding, consistent with the CLI. No raw file contents or decoder errors are shown to users.

| ID | Requirement | Regression evidence |
|---|---|---|
| EA9 | A stale asynchronous file read cannot overwrite a newer decision context | `event-audit-ui.test.cjs`: contract, file and example interruption cases |
| EA10 | Invalid UTF-8 produces no report, while valid UTF-8 still works | Encoding rejection and successful-file control in the same suite |

The five initial regression tests changed from four failures and one pass to five passes after the correction. The mocked DOM harness controls read completion deterministically; it is not a substitute for a live-browser smoke test or an exhaustive concurrency proof.
